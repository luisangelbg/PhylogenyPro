Maximum likelihood

The tree that gets published. Under an explicit model, likelihood searches for the topology and branch lengths that make the observed data most probable, and—unlike parsimony—it is consistent as long as the model is reasonable. This chapter explains the search, the fit with one model per partition, the four support measures with their four different thresholds, and how to formally test another author’s hypothesis.

5.1What it optimizes, and why it matters

The likelihood of a tree is the probability of having observed these data if that tree and that model were true. The maximum-likelihood tree is the one that makes that probability highest. It is reported as a logarithm, always negative, and less negative is better.

!A lnL on its own means nothing

Its absolute value depends on the number of sites and taxa. It only makes sense to compare likelihoods computed on exactly the same data. A lnL of −18,674 is neither “bad” nor “good”: it is the one for these data under this model, and it is only useful against another from the same alignment.

The decisive advantage over parsimony is the one from Chapter 1: under the correct model, likelihood is consistent, that is, with enough data it converges to the true tree even when there are unequal long branches. Parsimony, in that same geometry, converges with growing certainty to the wrong tree.

The condition “under the correct model” is not rhetoric. If the model is misspecified—unmodeled compositional heterogeneity, uncorrected saturation—likelihood is wrong too, and with more data it is wrong with more confidence. That is why Block 3 comes before this one.

5.2The model and the starting tree

The first row of controls sets the model: model (GTR, HKY, LG…), +G with so many categories, +I, and the frequencies, which can be empirical—counted in the alignment—or equal. The Use the model chosen in Block 3 button copies what won there, which is almost always the right thing to do.

iThe estimate them (+F) checkbox

By default the base frequencies are counted from the alignment, which is what phangorn::optim.pml does without optBf, and that is why the program’s results match its own. Turning on +F estimates them by maximum likelihood together with everything else, which usually gives a slightly better lnL. It is off by default to preserve that comparability, not because it is worse.

The starting tree can be the parsimony (Block 4) tree, the distance (Block 4) tree, BIONJ, or a random one. This is no minor detail: the search is heuristic, and where it starts determines which local optimum it may get stuck in. Trying two different starting points and reaching the same lnL is the best evidence that the search was enough.

5.3The search: NNI, SPR and the radius

The search starts from the starting tree and tries rearrangements: first NNI, which swaps neighboring branches, and then SPR, which cuts a whole branch off and grafts it back somewhere else. The rearrangements menu lets you use NNI only or NNI + SPR.

Two controls govern the cost:

  • SPR radius: the maximum distance, in number of branches, at which regrafting is allowed. A small radius is fast and explores little; a large one explores a lot and takes long. Five is a reasonable balance.
  • max rounds: how many complete passes of rearrangements are made before stopping.
∑Why the search is fast without cheating

Scoring each candidate by reoptimizing the whole tree would be unfeasible. The program does what PhyML and RAxML do: for each move, it reoptimizes only the branches the move touched, relying on the incremental computation of the likelihood engine. SPR also runs in two passes: first all candidates are scored with the inherited branch lengths—RAxML’s “lazy SPR”—and then only the best dozen are scored again with their neighborhood reoptimized. The winning tree is refitted in full at the end.

5.4Reading the result

The tiles summarize the run: the log-likelihood, the number of parameters (branches plus model), AIC and BIC, how many rounds were needed and how many topologies were evaluated, the time, and the estimated model parameters—the gamma α and κ or the relative rates.

Below the tiles, the panel writes out in prose what they mean. Two things deserve attention:

  • The number of rounds. If the search ended in a single round, it may not have explored anything; if it used up the maximum, it was probably still improving and you should raise it.
  • The α. Below 1 there is strong heterogeneity among sites, and not modeling it would have distorted the long branches.

5.5One model per partition

A chloroplast gene and nuclear ITS do not evolve at the same rate nor with the same composition. The partitioned fit acknowledges this without breaking the tree: all partitions share the topology and the branch proportions, but each has its own model and a rate multiplier, normalized to a site-weighted mean of one.

So a partition with a multiplier of 0.3 evolves at a third of the mean rate, and one with 2.5, two and a half times faster.

iWhy the fit starts out “tied”

Releasing all partitions from the very start made the search fall into a worse optimum. The program starts with all of them sharing one model during the first passes and releases them afterward. It is an implementation detail, but it explains why the partitioned result never falls below the single model it contains.

!Partitioning does not resolve a real conflict

Giving each gene its own rate does not free it from sharing the tree. If two genes have genuinely different histories—chloroplast capture, hybridization—the partitioned analysis averages them more elegantly, but it averages them all the same. Uncovering them is the job of Block 11.

5.6The four support measures

This is the section of the chapter that prevents the most mistakes. The program computes four measures, and they do not mean the same thing nor are they read against the same threshold.

Table 5.1. The four support measures, with their conventional threshold.
MeasureThresholdWhat it measures
Classical bootstrap≥ 70In what percentage of alignments resampled with replacement the branch reappears. Conservative: 70 is already fair support.
Ultrafast bootstrap (UFBoot)≥ 95An approximation by RELL, built to be nearly unbiased. Its scale is not that of the classical bootstrap.
SH-aLRT≥ 80Compares the likelihood of the tree with that of the two NNI rearrangements of that branch. A different question, not another version of the same one.
aBayes—A fast Bayesian approximation on the same local comparison.
✕The most common mistake with UFBoot

Reading it with the classical bootstrap threshold. Because UFBoot is nearly unbiased, it is less conservative: a UFBoot of 90% is not equivalent to a bootstrap of 90% but to considerably less support. That is why its threshold is 95 and not 70. The header of the on-screen table has the threshold written in, precisely so they are not confused.

Current practice in the literature is to require both: SH-aLRT ≥ 80 and UFBoot ≥ 95. They are different information—one measures whether the branch improves the likelihood, the other whether the signal holds up under resampling—and a branch that passes both is much better supported than one that passes only one.

✦What none of the four measures

Whether the tree is correct. All four measure the internal consistency of the signal under the method and model used. If the model is wrong, all four will support the wrong branch, and with more data they will support it more. High support is necessary, not sufficient.

5.7Testing a hypothesis

Here the block stops describing and starts testing. The question is: do my data reject the tree proposed by another author, or the one my hypothesis proposes?

It is done in two steps:

  1. Select the taxa of the group being tested and press Search for the best tree under that constraint: the program searches for the best tree forcing that group to be monophyletic. That is the best possible case for the hypothesis.
  2. Press Compare the trees (KH, SH, AU): the three tests contrast the constrained tree against the unconstrained one, using RELL replicates.

A p-value below 0.05 rejects the alternative tree. Of the three, the AU test is the one that best corrects for selection bias and the one you should report; KH and SH are there because they are still requested.

!“Not rejected” is not “just as good”

With few data almost nothing is rejected, and with many almost everything is. A nonsignificant result says that your data are not enough to rule out that hypothesis, not that it is correct. And the set of trees to compare must be fixed before looking at the results: choosing afterward what to compare is exactly the bias the AU test tries to correct.

5.8Threads, and why it takes as long as it does

The bootstrap and the Bayesian chains are spread over browser threads, built from the program’s own code. Two measured facts are worth knowing:

  • A freshly created thread runs interpreted and only reaches optimized code after a few seconds of repeating the same loops. That is why 16 replicates on 16 threads take longer than the same 16 on six: each thread pays its whole warm-up and throws it away. The program never assigns fewer than three jobs per thread.
  • One hundred maximum-likelihood bootstrap replicates take minutes. This is JavaScript, not C, and the page says so before starting, with an estimate and a cancel button.

If the browser does not allow threads—some configurations block them—the work is done in the page, slower but without failing.

5.10Common mistakes

✕Reading UFBoot with the bootstrap threshold

Already said, and repeated because it is the most common: 70 for the classical bootstrap, 95 for the ultrafast one, 80 for SH-aLRT. Three measures, three thresholds.

✕Searching only once, from a single starting tree

The search is heuristic and does not guarantee the optimum. If two different starting points reach different lnL values, the higher one rules and the search had not finished. Reaching the same one is the only reasonable evidence that it had.

✕Comparing lnL across different alignments

Removing three columns changes the lnL, and not because the tree is worse. Likelihoods are only compared on exactly the same data: same alignment, same columns, same taxa.

✕Presenting a constrained tree as “the tree”

The constrained tree is the best case for the hypothesis being tested, not an estimate. It is computed in order to compare it, and what gets published is the comparison—the lnL of both and the p-value of the AU test—not the constrained tree by itself.

✕Believing that high support validates the model

It is the other way around: support is computed assuming the model. If Block 3 warned of compositional heterogeneity or saturation, a UFBoot of 100 does not refute it; it repeats it with more confidence.
